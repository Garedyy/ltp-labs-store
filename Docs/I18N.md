# Internationalisation

English (default) and Portuguese (pt-PT), with remix-i18next 8 + i18next 26 + react-i18next 17.
Specification: `PROJECT_PLAN.md` §3.5. The locale is the first path segment; the server owns it.

## Locale routing

| Request                                                                     | Result                                                                                             |
| --------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `/`                                                                         | 302 to `/{detected}` — `lng` cookie → `Accept-Language` → `en` (`Vary: Cookie, Accept-Language`)   |
| `/en/…`, `/pt/…`                                                            | rendered in that locale (the URL is authoritative; no `?lng=`, no cookie, no header at this layer) |
| `/EN/cart`                                                                  | 301 to `/en/cart`                                                                                  |
| `/products/3`, `/xx/cart`                                                   | 302 to `/{detected}/products/3`, `/{detected}/xx/cart` (which is a translated 404)                 |
| `/en/`                                                                      | matches the `:lang` index (catalogue) — verified by `i18n.spec.ts`                                 |
| `/favicon.ico`, `/robots.txt`, `/.well-known/…`, any `:lang` containing `.` | 404, no redirect (asset deny-list)                                                                 |

The validation lives in a **middleware** on `routes/locale-layout.tsx` because parent and child
loaders run in parallel: a loader could not stop children from running with a bad locale.

`app/middleware/i18next.ts` configures remix-i18next with `order: ["custom"]` and a `findLocale`
that reads `url.pathname` (the normalised `url` from the middleware args — no `.data` suffix).
`getLocale(context)` / `getInstance(context)` give loaders the locale and a ready `t`.

`app/i18n/detect-locale.server.ts` (`detectLocale`, `localeFromAcceptLanguage`) serves only `/`
and the un-prefixed redirect; it is unit-tested.

## Entries

- `entry.server.tsx` wraps `<ServerRouter>` in `<I18nextProvider i18n={instanceFor(loadContext)}>`
  where `instanceFor` is `getInstance(loadContext)` with a module-scope EN fallback instance for
  errors thrown before the middleware ran.
- `entry.client.tsx` initialises i18next with `lng` from `<html lang>` and downloads only that
  locale's resources (`app/i18n/load-locale.client.ts`, one Vite chunk per language) **before**
  `hydrateRoot` (otherwise raw keys would mismatch the server HTML). `root.tsx` loads the other
  bundle on demand if a client navigation ever changes the locale. No browser language detector
  is installed.
- `root.tsx` sets `<html lang dir>` from the root loader (`getLocale`), renders one
  `<link rel="alternate" hreflang>` per locale plus `x-default` (→ EN), and syncs
  `i18n.changeLanguage` on client navigations that change the locale.

## Resources (`app/locales/`)

One namespace, `translation`, assembled from domain files: `common`, `catalogue`, `product`,
`cart`, `pages`, `errors`. `app/locales/index.ts` exports `{ en, pt }`.

- Every PT file ends with `satisfies typeof en` (type import of the EN file): a missing or extra
  key **fails `tsc`**. Demonstrated in PR #4.
- `app/i18n/i18next.d.ts` types `t()` keys from the EN resources (`returnNull: false`).
- `app/i18n/locales.test.ts` checks, for every locale: no empty value, no value equal to its key,
  identical `{{placeholder}}` sets per key, every plural suffix required by
  `LOCALES[locale].plurals`, and a plural suffix on every key that interpolates `{{count}}`
  (issue #20: an unsuffixed key rendered "1 results").

### Conventions

- camelCase keys, `{{placeholder}}` interpolation, never concatenate fragments.
- Plurals: `key_one` + `key_other` in EN **and** `key_many` in both locales (i18next has no
  `_many → _other` fallback); `_zero` when the zero message differs. i18next runs with `lng: "pt"`,
  whose CLDR rules put 0 in the `one` category ("0 resultado"), so any PT key that can receive
  `count: 0` needs a `_zero` form.
- No money, numbers, dates or HTML inside strings — formatting happens in loaders; `<Trans>` only
  for a link inside a sentence.
- Components never contain literal UI text (`eslint-plugin-i18next/no-literal-string`); design
  system primitives take labels as props.
- `common.brand` stays "The Online Store" in every locale (rendered uppercase by CSS so screen
  readers do not spell it).
- **Keyboard-safe characters only** (#38): UI strings use `-` (never the em dash U+2014 or the
  en dash U+2013), `...` (never the ellipsis U+2026), `"` (never the curly quotes U+201C/U+201D)
  and `x` for dimensions (never U+00D7), so every string can be typed and searched on a
  Portuguese keyboard. Accented letters and the pt-PT `«»` are fine. `locales.test.ts` fails on
  any other character; the same rule applies to the `<title>` separator in `lib/meta.ts` and to
  the discount sign in `CartSummary`.

## Adding a language (3 steps)

1. Copy `app/locales/en/` to `app/locales/<code>/` and translate; keep the `satisfies typeof en`
   lines — `tsc` lists every missing or extra key.
2. Add `<code>` to `LOCALES` in `app/i18n/config.ts` (`htmlLang`, `intlLocale`, `dir`,
   `nativeName`, plural suffixes).
3. Add it to `app/locales/index.ts`.

Routing, redirects, the switcher, hreflang, cookie, formatting, unit tests and the Playwright
locale list all derive from `LOCALES`.

## Formatting (`app/i18n/format.server.ts`, loaders only)

| Function                                             | Output                                                     |
| ---------------------------------------------------- | ---------------------------------------------------------- |
| `formatPrice(cents, locale)`                         | `$19.99` / `19,99 US$` (`Intl.NumberFormat`, currency USD) |
| `formatNumber(value, locale, maxFractionDigits = 1)` | `4.6` / `4,6`                                              |
| `formatPercent(ratio, locale)`                       | `-15%` (sign always shown)                                 |
| `formatDate(iso, locale)`                            | `Apr 30, 2025` / `30/04/2025` (`dateStyle: "medium"`, UTC) |

Loader data carries the formatted string next to the numeric value; components never call `Intl`,
so server and client HTML are identical. Tests normalise non-breaking spaces
(`tests/helpers/text.ts`).

## Language switcher and cookie

`LanguageSwitcher` is a `<details>` pill inside `<nav aria-label="Language">`. Its panel is a
`<Form method="post" action="/:lang/set-language">` with a hidden `redirectTo` (current path and
query) and one submit button per other locale (`lang` attribute on each name); the current locale
is listed with `aria-current="true"`. The `set-language` action validates the locale and that
`redirectTo` is a same-origin path, writes the `lng` cookie (`httpOnly`, `SameSite=Lax`, one year)
and answers 303. **It is the only writer of the cookie**: opening a shared `/pt/…` link never
changes a visitor's remembered language. GET on the route is 405; invalid input is 400.

## Tests

- Unit: `detect-locale.server.test.ts`, `paths.test.ts`, `format.server.test.ts`,
  `locales.test.ts` (empty values, placeholders, plural suffixes, keyboard-safe characters);
  `tests/helpers/i18n.ts` builds an instance that throws on a missing key.
- E2E (`tests/e2e/i18n.spec.ts`, desktop / mobile / `pt` projects; `no-js.spec.ts`): redirects
  from `/` by `Accept-Language`, upper-case and un-prefixed paths, `/en/`, asset deny-list,
  translated 404 inside the shell, `html[lang]`, hreflang, cookie written only by the switcher,
  path and query preserved, 405/400 on the resource route, switching without JavaScript.

## RTL readiness

`LOCALES[locale].dir` feeds `<html dir>`; styles use logical properties only (`ps-`, `pe-`,
`start`, `end`, `text-start`), so an RTL locale needs no component change.
